# Snapshot fixture drift and the test-orchestration gap

Why [#870](https://github.com/wheresrhys/totf/pull/870)'s `aggregate_stats` column removal surfaced
only as a TypeScript compile error, with no test failure — and what to do about it. Filed by
[#884](https://github.com/wheresrhys/totf/issues/884), part of
[#873](https://github.com/wheresrhys/totf/issues/873).

**Headline:** nothing in this repo's automated checks can detect snapshot-fixture drift, in any
direction. The drift #870 hit is not an isolated miss — it is still sitting in `main` today, in nine
fixtures (see [Evidence 5](#5-nine-fixtures-in-main-still-carry-removed-columns-today)).

## What actually runs, and when

| Step | Where | Runs Supabase? | Regenerates fixtures? |
|---|---|---|---|
| `scripts/check-swarm-tools-staleness.sh` | pre-push | no | no |
| `npm run lint` (prettier + eslint) | pre-push, CI `lint` job | no | no |
| `npx tsc --noEmit` / `npm run type:check` | pre-push, CI `type-check` job | no | no |
| `npm run test:nowatch` / `test:ci` (app tests) | pre-push, CI `unit-tests` job | **no** | no |
| `scripts/e2e-select-suite.sh` (Playwright) | pre-push only | yes (local, pre-seeded) | no |
| `npm run test:integration` | manual only | yes (local, pre-seeded) | no |
| `npm run db:seed:e2e` → `generateSnapshots()` | **manual only** | yes | **yes** |

`npm run db:generate-snapshots` — and `db:seed:e2e`, which calls `generateSnapshots()` as its last
step — runs in **no** hook and **no** CI job. Fixtures are purely hand-regenerated and committed, so
every automated check only ever replays whatever is already checked in.

Two further facts confirmed against the configs rather than assumed:

- CI (`.github/workflows/ci.yml`) has exactly three jobs — `lint`, `type-check`, `unit-tests` — and
  **no Supabase service at all**. The `unit-tests` job fabricates a `.env.dev` pointing at
  `localhost:54321` with a dummy anon key; nothing is listening there. Every app test is therefore
  fully mocked by construction, and a fixture is only ever a mock return value.
- CI also runs **no** E2E job. (CLAUDE.md's suite table claimed "pre-push hook (diff-aware) + CI
  (full)" for E2E; that CI half was wrong and is corrected by this ticket.)

## Root cause

The ticket proposed a two-part hypothesis. Both halves are confirmed, but the mechanism of the
second half is narrower — and worse — than assumed.

### (a) Fixtures are never regenerated automatically — confirmed

A stale-but-still-parseable fixture keeps satisfying whatever narrower assertions its consuming test
happens to make. JSON has no schema, so a removed column simply lingers as an extra key that no
assertion reads.

### (b) `tsc --noEmit` was the only step exercising the RPC's declared shape — confirmed, but it never looked at the fixture

#870's type error came from **app source code**, not from fixture content: `SpBiometricsTab` and
`StatsHistoryChart.getSizes` read the removed fields off a value typed `AggregateStatsResult`. That
is the entire reason the type checker spoke up. The fixtures themselves are invisible to it, for two
independent reasons:

1. **Every fixture is consumed through a double assertion.** The universal pattern in app tests is
   `fixture as unknown as SomeType` (30+ occurrences — e.g.
   `app/(routes)/summary/__tests__/PageContent.test.tsx:9`,
   `app/components/__tests__/SpeciesTotalsTable.test.tsx:11`,
   `app/lib/__tests__/underlying-stats.test.ts:232`). Asserting through `unknown` switches
   assignability checking off completely, so the fixture's real shape is never compared against the
   RPC type at all.
2. **Even without the cast, a removal would still not be caught.** An imported JSON module is not a
   fresh object literal, so TypeScript's excess-property check does not apply to it. A fixture
   carrying columns the type no longer declares remains perfectly assignable. Dropping the casts
   would catch *added* columns (a stale fixture missing a newly-required property), but never
   *removed* ones — which is exactly the direction #870 moved in.

So the honest statement of the root cause is: **fixture content is not validated by anything.** Not
by the type checker, not by unit tests, not by E2E. `tsc` caught #870 by accident, via a consumer
that happened to read one of the removed fields.

## Evidence

### 1. The #870 fixture has zero consumers

`getSpeciesStatsHistory.alpha.robin.json` is imported by **no test file**. It is generated by
`scripts/generate-snapshots.ts` and read by nothing — confirmed by grep and by
`tsc --listFilesOnly`, which never pulls it into the program. No unit test could have caught its
drift, because no unit test touches it.

### 2. Three other fixtures are likewise orphaned

`fetchGraphableEncounterData.alpha.robin.json`, `fetchMistakes.beta.json`,
`fetchNotableRetraps.beta.json` — generated, committed, never imported. 23 of the 27 fixtures on
disk are in the `tsc` program; these four are not.

### 3. Eight fixtures have no generator at all

`generate-snapshots.ts` has 14 `writeSnapshot` calls producing 19 files (its own docstring says
"writes 19 JSON files"). The directory holds 27. The eight with no generating code are
`fetchHomePageSummaryStats.{alpha,zero}`, `fetchPulliEncounters.alpha`, `fetchResightings.alpha`,
`fetchRingSequenceControls.alpha`, `fetchSummaryStats.{alpha,zero}`, `fetchTopSpecies.alpha` — added
by hand in feature commits (e.g. `fetchTopSpecies.alpha.json` in "feat: add top species section to
home page") and never wired in. `npm run db:generate-snapshots` *cannot* refresh them; they can only
drift.

The two `.zero.json` files are legitimately synthetic edge cases (a hand-authored zero-activity row,
not a captured query result). The other six look like they should have been generated.

### 4. `scripts/` is not type-checked

`tsconfig.json`'s `include` covers `app/**`, `types/**`, `next-env.d.ts` and `.next/types/**` — not
`scripts/`. `generate-snapshots.ts` is only reachable from `seed-e2e-data.ts`, also outside the
program, so `npm run type:check` never checks the fixture *generator* either. (`lib/**` is checked
transitively, via imports from `app/`.)

### 5. Nine fixtures in `main` still carry removed columns today

All eight wing/weight columns #870 dropped from `aggregate_stats` are still present in:

| Fixture | Generated? | Still carries |
|---|---|---|
| `fetchSpeciesData.alpha.json` | yes | 8 wing/weight + `new_young_bird_count` |
| `fetchSpeciesData.beta.json` | yes | 8 wing/weight + `new_young_bird_count` |
| `fetchPayOffStats.alpha.json` | yes | 8 wing/weight + `new_young_bird_count` |
| `fetchPayOffStats.beta.json` | yes | 8 wing/weight + `new_young_bird_count` |
| `fetchSpPageData.alpha.robin.json` | yes | 8 wing/weight + `new_young_bird_count` |
| `fetchSummaryStats.alpha.json` | no | 8 wing/weight + `new_young_bird_count` |
| `fetchSummaryStats.zero.json` | no (synthetic) | 8 wing/weight + `new_young_bird_count` |
| `fetchHomePageSummaryStats.alpha.json` | no | 8 wing/weight |
| `fetchHomePageSummaryStats.zero.json` | no (synthetic) | 8 wing/weight |

`new_young_bird_count` was removed from `aggregate_stats` even earlier, by
[#824](https://github.com/wheresrhys/totf/issues/824). Five of these nine are regenerable right now
and simply were not regenerated; `npm run qa` and the full pre-push hook are green regardless. This
is the clearest possible demonstration that the gap is structural, not a one-off lapse in #870.

## Recommendations

Ordered by value-per-effort. None are implemented by #884 — it is an investigation ticket; each
needs its own ticket and its own USE-derived tests.

### R1 — Add a fixture-freshness check to the DB integration suite (highest value)

The DB integration suite is the only place in the repo with a live Postgres. Add a test there that
runs `generateSnapshots()` into a temp directory and diffs the result against the committed
`test-fixtures/snapshots/`, failing with the per-file diff. This catches drift in **both**
directions, needs no type-level trickery, and reuses machinery that already exists
(`supabase/__tests__/`, `npm run db:seed:e2e`). It only covers the 19 generated fixtures — which is
precisely why R3 matters.

Caveat to design around: the check is only meaningful against a DB seeded exactly as
`db:seed:e2e` leaves it, and the suite is explicitly documented as concurrency-safe across swarm
worktrees. A test that regenerates fixtures must write to a temp directory and must not mutate
shared rows, or it will collide with sibling worktrees.

### R2 — Make the pre-push hook run that check when the diff makes it relevant

CI cannot run it (no Supabase). Mirror the existing `scripts/e2e-select-suite.sh` idiom — the repo's
established pattern for "run an expensive, shared-resource check only when the branch's diff
warrants it" — and run the R1 test from the pre-push hook when the diff touches
`supabase/schema/`, `types/supabase.types.ts`, or `scripts/generate-snapshots.ts`. Any branch
changing an RPC's shape touches at least the first two, so the blast radius is right and most
branches pay nothing.

### R3 — Bring the ungenerated fixtures under the generator

Wire the six capturable ones from Evidence 3 into `generate-snapshots.ts`, and separate the two
genuinely synthetic `.zero.json` fixtures so their hand-authored status is explicit rather than
accidental — e.g. `generated/` vs `synthetic/` subdirectories, which dovetails with
[#882](https://github.com/wheresrhys/totf/issues/882)'s directory-by-source reorg. A fixture that no
generator produces should be a deliberate, visible choice.

### R4 — Delete or consume the orphaned fixtures

The four fixtures from Evidence 1 and 2 are pure liability: they cost regeneration time, imply
coverage that does not exist, and were the proximate cause of #870's confusion. Either wire them
into a test or delete them. Best folded into #882's reorg rather than done standalone.

### R5 — Drop the `as unknown as` casts where a direct assertion works

Replace `fixture as unknown as T` with `fixture satisfies T` / a typed binding wherever the fixture
genuinely matches the type. Partial protection only — it catches *added* columns, never removed ones
(see root cause (b)(2)) — and it will not compile until R1/R3 have brought the fixtures back in sync.
Do it after those, as a hardening pass, and expect some fixtures to legitimately need a cast
(`fetchSpPageData.alpha.robin.json` is a composite of several queries, not one RPC's row type).

**Deliberately not recommended:** adding a Supabase service to CI purely for this. It would slow
every PR for a check that R2 already places at the exact moment it can fire, and this repo's whole
DB-testing posture (integration tests manual, one shared local instance) is built the other way.
